## 1. Choice of Python, FastAPI, and Server-Side HTML

Date: 2026-09-25
Status: Decided
Context: The assignment requires a minimal single-process, single-container application running on SQLite with low operational complexity. I needed a stack that handles HTTP routing, data processing, and user interfaces without requiring separate background processes or complex build pipelines.
Decision: I selected Python with FastAPI for the backend API/routing and Jinja2 templates for server-side HTML rendering.
Alternatives considered: I considered Django for its features and because I used it last year, but rejected this decision because it was unnecessarily complex for a simple single-container app. I also considered using Java or Node.js but chose Python since i have more experience with it and prefered the straightforward data manipulation logic for ingredient unit conversions.
Consequences: This keeps third-party dependencies under the 12-package soft cap and ensures fast execution in a single container. However, server-side template rendering requires full page reloads for UI updates unless lightweight JavaScript is added later.

## 2. Domain Scoping & Modular Seams

Date: 2026-09-29
Status: Decided
Context: The application needs to separate recipe management from shopping list generation and pricing logic to maintain clear architectural boundaries and testability.
Decision: I created modular files inside the "catalog" folder and "shopping" folder, isolating domain queries and ingredient scaling calculations within service modules like "services.py"
Alternatives considered: Placing all route handlers and database queries inside a monolithic "main.py" file, this was rejected because it would make the code messy and hard to maintain/read.
Consequences: Improves maintainability, allows domain logic unit testing without external HTTP runtime overhead, and simplifies future domain expansion as well as adding new features.

## 3. Database Schema & Shopping List Pricing Calculation

Date: 2026-09-30
Status: Decided
Context: The catalog stores recipe details and ingredient quantities, while the shopping domain combines requirements across recipes and matches them to supermarket products to estimate checkout costs. The data model needs to represent these relationships without duplicating ingredient records.
Decision: In SQLite, I modeled recipes and ingredients as a many-to-many relationship through the "recipe_ingredients" junction table, which stores each recipe's amount and unit for an ingredient. Both domains share the "ingredients" table, "recipe_ingredients" links ingredients to recipes, while "supermarket_products" links one or more product and package-price options to an ingredient. For shopping calculations, I normalize the different units to base units (kg to g and L to ml) before aggregation, then round required quantities up to whole packages when estimating cost.
Alternatives considered: Duplicating ingredient names and details inside each recipe would make cross-recipe aggregation and product matching less reliable. Storing only one supermarket product directly on each ingredient would prevent an ingredient from having multiple product options. I also considered calculating fractional package costs (e.g., paying for half a carton of milk or 3 eggs), but that does not what would happen in real life. I also considered using DIV and MOD, but rejected in favor of the clearer package-ceiling calculation. I also considered adding a table with ingredients you already have but decided to finish the core app before adding new features.
Consequences: The shared ingredient records provide a consistent join point between both domains, while the junction table supports recipe-specific quantities and units. Multiple product records per ingredient allow the shopping logic to select the lowest-priced option and calculate whole packages needed, producing more realistic estimated costs.

## 4. Core Business-Logic Test Coverage

Date: 2026-10-03
Status: Decided
Context: The assignment requires automated tests for the core business logic of both domains and at least 70% coverage measured with a standard coverage tool. The catalog domain handles recipe search and serving-size scaling, while the shopping domain normalizes and aggregates ingredient quantities and estimates package-based prices.
Decision: I used pytest and pytest-cov to test the catalog and shopping service modules directly. Tests prioritize the main domain behaviors and meaningful branches, including title and ingredient search, valid and invalid serving targets, unit conversions, aggregation across recipes, package rounding, missing products, and empty or invalid selections. Test data is loaded into a temporary SQLite database so service behavior is exercised without depending on the application database.
Alternatives considered: I considered prioritizing HTTP endpoint and template tests, but those would have focused on framework integration rather than the requested actual logic.
Consequences: The measured combined coverage of the two service modules is 99.03% (catalog: 100%; shopping: 98%). Routing, templates, and some infrastructure behavior such as database initialization are covered more lightly because they are not the core business logic. The exact pytest-cov command and measured result are recorded in the README (as well as instructions to run the tests)

## 5. One thing you deliberately chose not to build and why - Home Inventory Tracking

Date: 2026-10-03
Status: Decided
Context: A shopping list could be more useful if it accounted for ingredients the user already has at home. This would require tracking household inventory and comparing it with the quantities needed for selected recipes.
Decision: I chose not to build a fridge inventory feature in this version. The application generates a shopping list from recipe requirements without subtracting items the user already owns. It does take into account if multiple recipes have the same ingredients
Alternatives considered: I considered adding a list of items already at home and reducing the shopping quantities accordingly. I also considered supporting inventory amounts and units, but that would require additional tracking and matching behavior beyond generating a recipe-based shopping list. Another feature that can be added later on is editing and creating new recipes.
Consequences: The application remains focused on recipe based shopping list generation and package/product cost calculations, with less data entry and complexity. Users may see items on the list that they already have and inventory tracking can be added later as a separate feature.

## 6. Services separation and domain ownership

Date: 2026/11/16
Status: Decided
Context: Assignment 2 requires the original application to be split into two independent services (one for each feature domain). They must have their own separate databases and communicate over HTTP across the domain boundary. In Assignment 1, I established the boundary between recipe management and shopping list generation and pricing. However, both domains shared tables in the database. For Assignment 2, I will have to split the services and change the database setup since they are no longer allowed to share database tables.
Decision: The application has been split into two independent FastAPI services. The Catalog Service is responsible for recipes, ingredients, the relationships between recipes and ingredients, and the HTTP endpoints for retrieving recipe information and ingredient quantities. The Shopping Service is responsible for supermarket products and pricing information, shopping list aggregation, and packaged cost calculations. The cross-service communication flow is entirely server-side.
The client sends a shopping list request to the Shopping Service containing the recipe IDs and requested serving counts. The Shopping Service then requests the relevant recipe information from the Catalog Service over HTTP. The Catalog Service returns the recipe details and ingredient quantities, scaled to the requested serving counts. The Shopping Service then aggregates the returned ingredients, queries its own supermarket product data, and calculates the required packages and estimated costs. If the Catalog Service is unavailable, the Shopping Service returns an HTTP 503 response. If the Catalog request times out, the Shopping Service returns HTTP 504. If the Catalog Service returns an unexpected error, the Shopping Service returns HTTP 502. If a recipe is missing, it is treated as unavailable recipe data rather than attempting direct database access across the service boundary.
Alternatives Considered: Having the UI call both services was rejected because the requirements specify that at least one flow must cross the service boundary server-side.
Consequences: The original feature/domain boundary has been maintained, and each service now has its own independent codebase and database ownership. The Shopping Service now depends on the Catalog Service when generating shopping lists.

## 7. Data and migrations

Date: 2026-11-17
Status: Decided
Context: Assignment 2 requires the original application database to be divided into one SQL Server database per service. Each service must own and protect only its own data, while existing data must be preserved. The original database also contained a cross-domain foreign key that cannot remain across two databases.
Decision: SQLAlchemy with the 'pymssql' driver reads 'DATABASE_URL' in both services. The migration generator in 'scripts/generate_migration_sql.py' extracts data from 'data/app.db' and creates '001_init.sql' in each service migration directory while preserving original record IDs. The Catalog database owns 'recipes', 'ingredients', and 'recipe_ingredients'; the Shopping database owns 'supermarket_products'. Each service login has access only to its own database.
The Shopping database stores 'ingredient_id' as a plain external reference instead of a cross-database foreign key. Ingredient and recipe details are validated through HTTP calls to the Catalog service, as Shopping must not read the Catalog database directly. At startup, each service connects with retries and exponential backoff to tolerate Azure SQL cold-start pause (error 40613). Each service creates 'schema_migrations' if needed, applies sorted migration files once, and records a version only after that migration completes. '001_init.sql' creates and seeds each service's tables. '002_add_is_active.sql' alters an existing populated table and adds 'is_active' with a default value and 'WITH VALUES', preserving existing rows. Migrations are forward-only and applied migration files are never edited.
If a migration fails, startup stops and the failed version is not recorded. A safe issue is corrected with a new forward migration and redeployment. If data or schema is corrupted, the Azure SQL database is restored from the latest backup or a point-in-time restore, the data and schema are verified, and deployment resumes. The Azure recovery procedures remain to be demonstrated in the deployed environment.
Alternatives Considered: A migration framework was considered, but numbered SQL files with a small service-specific runner provide explicit SQL Server control and make migration order easy to inspect. Down-migrations were rejected in favor of forward corrective migrations and database restore-based recovery.
Consequences: Catalog and Shopping can evolve independently, apply each migration once and preserve existing rows when schemas change. Removing the cross-database foreign key replaces database referential integrity with HTTP validation in the Shopping flow. A bad migration can block startup, but a recorded migration cannot be silently rerun or corrected by editing its original file.

## 8. Static UI and serverless Azure hosting

Date: 2026/11/18
Status: Decided
Context: Assignment 2 requires the server-rendered Assignment 1 pages to become a static UI that calls two independently deployed services. The deployment must use pay-per-use Azure resources, scale to zero when idle, keep the services separate, and give each service its own serverless SQL database. The final deployment contract specifies Azure Storage static website hosting for the UI.
Decision: The UI is implemented as static HTML, CSS and JavaScript in 'ui/' and is uploaded to one Azure Storage account with static website hosting enabled. It reads the Catalog and Shopping base URLs from 'config.js', which is replaced or generated for each environment instead of being hardcoded in the application logic. Locally, the same files are served by 'nginx:alpine' in Compose without a frontend Dockerfile. The Catalog and Shopping APIs are deployed as two separate Azure Container Apps in one Consumption-plan Container Apps environment. Both Container Apps have a minimum replica count of zero and a maximum of one. The databases are two Azure SQL Database serverless databases on one logical Azure SQL server: one database and login for Catalog and one database and login for Shopping. The databases use the serverless tier with auto-pause, so compute is billed according to use rather than running continuously. Images are stored in GitHub Container Registry, and the UI is hosted separately from the backend containers. Both APIs accept browser requests only from the configured 'UI_ORIGIN'.
Alternatives considered: A frontend framework was considered, but plain static files avoid a frontend build runtime and an additional container. Azure Static Web Apps was considered, but the final assignment contract specifies an Azure Storage static website, so Storage is the selected hosting target. Always-on Container Apps or a dedicated workload profile were rejected because they introduce fixed compute costs and would go against the assignment instructions.
Consequences: When idle, the Container Apps can scale to zero and the Azure SQL serverless databases can pause, reducing cost but making the first request slower. A request may need to wait for the container cold start and for SQL Database to resume. The services therefore retry SQL connections with exponential backoff when Azure error 40613 occurs. On startup, each single-replica service runs its pending migrations before serving requests. The one-replica limit prevents two startup instances from applying migrations concurrently, but it also limits throughput and availability. A migration failure prevents that service from starting and must be corrected with a new forward migration or database recovery. 'config.js', 'UI_ORIGIN', database connection strings, and service URLs must be supplied separately for local and Azure environments.
At 100x traffic, this design would need reassessment: Container Apps would require higher maximum replicas, database capacity and connection pooling would need to increase, and migrations would need a coordinated release mechanism rather than relying only on single-replica startup. Caching, asynchronous work, and a dedicated or pre-warmed compute tier could be considered however have an additional cost and operational complexity.

## 9. Pipeline and testing

Date: 2026/11/19
Status: Decided
Context: Assignment 2 requires testing the two split services independently and verifying at least one user-visible flow across the service boundary. The original Assignment 1 tests worked on the monolith and its SQLite database, so I have to create new ones to prove that the SQL Server-backed services, HTTP seam, Compose startup, or partial-failure behavior work.
Decision: Each new service has its own test suite and development dependency manifest. Catalog tests cover recipe scaling, search/detail mapping, image fallback, and missing recipes. Shopping tests cover unit normalization, aggregation, package pricing, empty or missing selections, and controlled Catalog-unavailable errors. Core service coverage is measured only from these new Assignment 2 suites. The current Catalog suite achieves 94.29% and Shopping achieves 86.08%. A cross-seam integration test starts a local HTTP Catalog stub, invokes Shopping's real outbound HTTP client, and uses a deterministic fake for Shopping's own database. This keeps the test repeatable without Azure or a live SQL Server while still checking the service boundary. I manually tested compose separately for full startup, migrations, health, static UI delivery, and stopping Catalog while Shopping remains healthy. The GitHub Actions CI pipeline is planned for Day 5 (I am currently on day 4 of my implementation). It will gate pull requests and pushes with linting, the service unit and cross-seam tests, separate 70% coverage checks, OpenAPI and system.yaml schema validation, and Docker image builds. Once CI and branch protection are configured, these checks will prevent unverified code from being merged into main or deployed to Azure.
Alternatives considered: Running every unit test against Azure SQL was rejected because CI must not wake or modify billable Azure databases. Requiring a full Compose stack for every unit test was rejected because it is slower and makes pure business-logic failures harder to isolate. A mocked function that bypassed HTTP entirely was rejected for the cross-seam test because it would not verify the actual URL, timeout, response parsing, and error mapping path.
Consequences: The tests are fast and deterministic, and each service can be tested without the other service's database. The HTTP stub does not reproduce every behavior of the real Catalog container, so the Compose smoke test remains necessary and is the evidence for real container networking and startup order. Azure-specific tests such as SQL pause/resume, Container Apps ingress, and deployment health checks are not performed or written in local unit tests; it will be verified during deployment and CI/CD work. The original 'tests/' directory remains only as temporary, just like the rest of the monolithic app.
